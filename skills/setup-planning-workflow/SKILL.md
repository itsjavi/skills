# Dev Pairing Workflow Bootstrap

Bootstrap a docs-first **Dev Pairing (AI + human dev) workflow and plan bookkeeping** structure for projects that do not
yet have one.

## When To Use

Use this skill when asked to add planning conventions, ADRs/decision records, PRD/product docs, plan/checkpoint
workflows to a new or under-documented repo.

Do not use it for implementing an existing plan. Use the plan handoff or plan creator skills for that.

## Goal

After bootstrapping, future coding agents should understand how to:

- read the product requirements and decisions before coding
- create and update decision records
- create implementation plans from requirements/decisions
- implement plans phase-by-phase
- resume from the current milestone/plan/checkpoint state
- create checkpoints after phases
- add dated implementation updates when code changes make docs stale
- avoid touching git staging unless explicitly asked
- fetch current library/tool documentation with Context7 before answering library-specific questions or implementing
  against unfamiliar/current APIs

## Target Structure

Create or adapt this structure:

```text
docs/
  PRODUCT.md
  MILESTONES.md
  ENV_VARS.md
  SECURITY.md
  DESIGN.md                  # optional; generated by a design skill when needed
  templates/
    DECISION.md
    PLAN.md
    PLAN_CHECKPOINT.md
  decisions/
    README.md
  research/
    README.md
  plans/
    README.md
  checkpoints/
    README.md
  setup/
    README.md
```

## Document Roles

- `PRODUCT.md`: master product requirements document (PRD). High-level requirements, constraints, scope, non-goals,
  operating assumptions.
- `MILESTONES.md`: master implementation state. Milestones, plan execution order, status, dependencies, reasoning, and
  what is next.
- `decisions/`: architecture/product decision records. Durable, load-bearing decisions.
- `plans/`: implementation plans written after product requirements and decisions are clear. Plans are divided into
  phases.
- `checkpoints/`: implementation checkpoints for plan phases. Capture what changed, checks run, surprises, and
  follow-ups.
- `research/`: brainstorms, AI chats, spike notes, comparisons, rough thinking. Can become stale.
- `setup/`: local dev, self-hosting, deployment, and operational setup guides.
- `ENV_VARS.md`: env var catalog with purpose, default, required/optional, scope, and security notes.
- `SECURITY.md`: security model, threat assumptions, secret handling, reporting process, and operational hardening.
- `DESIGN.md`: master design guidelines. If present, follow it for UI work; if missing and UI work is requested, suggest
  generating it with the create-design-guidelines skill.

## Bootstrap Workflow

1. Inspect the repo first:
   - existing docs
   - package/framework hints
   - README
   - existing setup/security/env files
2. Preserve existing content. Do not overwrite useful docs; merge or add dated sections.
3. Create missing directories and files from the target structure.
4. Fill templates with concise, reusable structure.
5. Seed `PRODUCT.md` and `MILESTONES.md` with what can be inferred; mark unknowns as `TBD`.
6. Add or update an agent guide (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules`, or equivalent) with the workflow in **Agent
   Guide Requirements** below.
7. Run formatter/checks appropriate for markdown if available.

## Agent Guide Requirements

Add a concise section that tells coding agents to follow this order every fresh session:

1. Read the agent guide.
2. Read `docs/PRODUCT.md`.
3. Skim `docs/decisions/README.md`.
4. Read decisions related to the current work.
5. Read `docs/MILESTONES.md`.
6. Read the active plan and latest checkpoints.
7. For UI work, read `docs/DESIGN.md` if present.

Also include these rules:

- Plans are implemented phase-by-phase.
- Update a plan status table when starting/completing a phase.
- Create a checkpoint in `docs/checkpoints/` after each completed phase.
- The final phase is always **Final review pass**.
- If not working inside a plan, update the closest relevant doc in the same turn for behavior, architecture, config,
  API, operational, or user-facing changes.
- For post-plan changes, add `## Implementation update (YYYY-MM-DD)` to the relevant existing plan/doc instead of
  rewriting history.
- Accepted decision records are not substantively edited; write a superseding decision record instead.
- Keep implementation and docs in sync as a final step before finishing.
- Never alter the git index or status: do not stage, unstage, amend, reset, or switch files between staged/unstaged
  unless explicitly asked.
- Do not create commits unless explicitly asked; commit messages use Conventional Commit format.
- Use Context7 (`npx ctx7@latest`) to fetch current docs for library/framework/SDK/API/CLI/cloud questions and
  implementation details.

## Workflow Docs To Generate

`docs/MILESTONES.md` should include:

- status legend
- drafted plans table
- roadmap / milestone groups
- recommended execution order
- how to draft a new plan
- how to resume work from the current state
- links to templates

`docs/decisions/README.md` should include:

- decision filename convention
- status lifecycle (`Proposed`, `Accepted`, `Superseded by NNNN`, `Deprecated`)
- index table
- rule to supersede accepted decisions instead of rewriting them

`docs/plans/README.md` should include:

- plan filename convention
- phase/checkpoint convention
- phase workflow
- final review workflow
- docs-sync rule for implementation updates

`docs/checkpoints/README.md` should include:

- checkpoint naming convention
- required checkpoint content
- how checkpoints link back to plans

## Agent Guide Sections To Generate

Generate these sections in the target project's agent guide, adapted to the repo.

### Keep implementation and docs in sync

- When changing behavior, architecture, configuration, APIs, operational flows, or user-facing workflows, update
  relevant docs as a final step.
- If working inside an active plan, follow that plan's status/checkpoint workflow.
- If not working inside a plan, add a dated section to the closest relevant existing plan or doc instead of rewriting
  history, for example `## Implementation update (2026-05-11)`.
- Use implementation updates to explain what changed, why it differs from the original plan if applicable, and any
  follow-ups.
- Do not add docs churn for purely mechanical refactors that do not change behavior or intent.
- Before finishing, briefly check whether the code change makes existing docs stale.

### Using git

- Never alter the git index or status unless explicitly asked.
- Do not stage, unstage, amend, reset, or otherwise switch files between staged and unstaged.
- Do not create commits unless explicitly asked.
- Commit messages must use Conventional Commit format: `<type>(optional-scope): <imperative summary>`.
- Allowed types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `build`, `ci`.

### Fetching documentation

- Use `npx ctx7@latest library <name> "<user question>"` before answering or implementing against
  library/framework/SDK/API/CLI/cloud details.
- Pick the best `/org/project` match, then run `npx ctx7@latest docs <libraryId> "<user question>"`.
- Do not use Context7 for business-logic debugging, reviews, refactors, or general programming concepts.
- Do not include secrets in Context7 queries.
- If Context7 quota fails, tell the user how to raise limits. If network/DNS fails in a sandbox, retry outside the
  sandbox when the environment supports it.

## Template Minimums

`DECISION.md`:

- title, status, date, owner
- context
- decision
- consequences
- alternatives considered
- follow-ups

`PLAN.md`:

- status table
- goal
- definition of done
- out of scope
- phases with acceptance checks
- test/validation plan
- risk notes
- final review phase

`PLAN_CHECKPOINT.md`:

- completed date
- summary
- files changed
- checks run
- notes/surprises
- implications for decisions/product/future plans
- follow-ups

## Rules

- Keep docs concise and operational.
- Prefer updating existing docs over duplicating them.
- Use dated sections for post-hoc updates, e.g. `## Implementation update (2026-05-11)`.
- Decisions belong in `decisions/`; implementation sequencing belongs in `plans/`; status/order belongs in
  `MILESTONES.md`.
- Do not invent major product requirements. Mark unknowns as `TBD`.
- Do not stage, unstage, or commit.
